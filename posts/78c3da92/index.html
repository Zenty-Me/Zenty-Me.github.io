倒排索引

认识

倒排索引是从关键词到文档的映射。它与传统的正排索引不同，正排索引存储的是文档及其内容，而倒排索引反其道而行之，存储的是每个关键词以及包含这些关键词的文档信息。

简单示例：

假设我们有以下文档，分别对应一条中文句子：

  • 文档 1: Elasticsearch 是分布式引擎
  • 文档 2: 分布式系统的核心是搜索
  • 文档 3: 搜索引擎的未来是智能化

倒排索引将这些文档转化为如下形式：

关键词 文档 ID
elasticsearch 1
分布式 1, 2
系统 2
核心 2
搜索 2, 3
引擎 1, 3
智能化 3

当用户搜索某个关键词，如“引擎” 时，Elasticsearch 可以通过倒排索引快速查找到关键词对应的文档 ID（文档 1 和文档 3），而无需扫描所有文档。

常用属性

顶层控制属性

dynamic

场景：你定义了 title 是 text，结果代码不小心多传了个 age 字段。

  • dynamic: true（默认）：ES 默默帮你在映射里加上 age，类型可能错判成 long，导致后续范围查询异常。
  • dynamic: strict（推荐）：直接拒绝写入，返回明确报错，倒逼你修正代码。

示例（严格模式下的报错）：

fields + ignore_above

场景：title 既要全文搜索（用 text），又要按字母排序（必须用 keyword）。同时，为了防止有人存超长文本撑爆内存，用 ignore_above 切断。

copy_to

场景：用户想搜索 title 或 content，不想分两个字段查，希望一个 full 字段覆盖所有。用 copy_to 把多个字段的内容复制到一个隐藏字段里。

format

场景：你的数据来源复杂，有时候传 "2026-09-05"，有时候传 "2026/09/05"，默认的 ES 只认 ISO 标准（2026-09-05T10:30:00Z），不认斜杠。

null_value

场景：有些文档的 tags 字段没填，是 null。默认情况下，null 值不会建立倒排索引，你搜 tags: "NULL" 搜不到。如果你想统一把空值替换成占位符，就用 null_value。

normalizer

场景：存邮箱或用户名，用户搜 "Admin" 想命中 "admin"，但 keyword 是精确匹配，区分大小写。用 normalizer 在索引时统一转小写。

字段级属性

index：搜索开关

场景：有些字段（如内部 ID、base64 图片、加密数据）只需要随文档返回展示，永远不需要被搜索。关闭索引可以节省大量磁盘空间和写入 CPU。

analyzer vs search_analyzer

场景：索引时希望尽可能多地切词（提高召回率），搜索时希望更符合用户意图（提高精准度）。比如中文搜索，索引用 ik_max_word（细粒度），搜索用 ik_smart（粗粒度）。

doc_values

核心原理：text 类型默认 doc_values: false（因为分词后无法做精确排序/聚合），keyword 和数值类型默认 true。如果你错误地关闭了它，排序和聚合会直接报错。

coerce

场景：你定义字段为 integer，但数据源传来 "10.0"（字符串带小数点）。默认 coerce: true 会自动转成整数 10，不会报错。如果你希望严格校验，就关掉它。

properties

场景：你的文档里有一个嵌套的 user 对象，包含 name 和 age。必须在 properties 里再定义一次内部字段，否则 ES 会动态映射，类型可能不准。

enabled

场景：你需要存储一个巨大的、结构不固定的 JSON（如第三方回调的原始报文），只是存着将来展示用，永远不需要在内部字段上做搜索或聚合。开启 enabled: false 可以节省大量索引开销。

  • text：会分词，用于全文模糊搜索（如百度搜索文章内容）。默认不支持排序和聚合。
  • keyword：不分词，整个值作为一个整体，用于精确匹配、排序、聚合统计（如状态码、分类、邮箱）。

注意：_search 是固定路径。

常用查询功能详解

Elasticsearch 的查询 DSL 主要分为叶子查询（在单个字段上查询）和复合查询（组合多个叶子查询）。

1. 全文检索

这类查询会对输入的搜索文本进行分词，然后用分词结果去匹配索引中的内容，并根据相关性（_score）排序。

  • match** 查询**：最常用的全文搜索，用于在一个指定字段中进行分词匹配。

示例场景：在图书描述中搜索包含“分布式”或“搜索引擎”的书籍。

  • multi_match** 查询**：match 的增强版，允许在多个字段中同时进行全文搜索。
  • <font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">match_phrase</font> 查询：要求分词后的所有词项必须全部出现在文档中，并且顺序一致、位置连续（允许通过 **<font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">slop</font>** 参数调整间隔）。它不会像 <font style="color:rgb(15, 17, 21);background-color:rgb(235, 238, 242);">match</font> 那样将词项拆开独立匹配，而是当作一个整体短语来查找。

补充：

在Elasticsearch中，operator主要用于match系列查询（如match、multi_match），其核心作用是控制多个搜索词之间的逻辑关系，决定文档需要满足“任意一个”还是“全部”搜索词才算匹配。

它接受两个值，默认为or：

  • or** (默认值)：只要文档包含任意一个**搜索词，就算匹配。例如，搜索“quick brown fox”，只要文档包含quick、brown或fox中的任意一个词就会被召回。
  • and：文档必须同时包含所有搜索词，才算匹配。例如，搜索“quick brown fox”，文档必须同时包含quick、brown和fox这三个词才会被召回。

示例对比：
假设索引中有两篇文档：

  • 文档A: "I love cats"
  • 文档B: "I love dogs"

执行查询 "match": {"content": {"query": "cats dogs"}}：

operator 参数 逻辑 匹配结果
"or"** (默认)** cats OR dogs 文档A和文档B都会被匹配，因为每篇文档至少包含其中一个词。
"and" cats AND dogs 两篇文档都不会被匹配，因为没有文档同时包含cats和dogs。

2. 精确查询

这类查询不会对输入文本进行分词，而是将整个输入作为一个词条，与字段中的精确值进行匹配。通常用于 keyword、数值、日期等类型的字段。

  • term** 查询**：用于查找与指定值完全相等的文档。

注意：不要用 term 查询 text 类型的字段，否则可能查不到结果。

  • terms** 查询**：term 的复数版本，用于匹配多个精确值中的任意一个。
  • range** 查询**：用于查找字段值在指定范围内的文档。

同样适用于日期范围，如 publish_date 在 "2023-01-01" 之后。

3. 复合查询

主要用于组合多个查询条件，其中 bool** 查询**最为核心和常用。它包含四个子句：

  • must：条件必须满足，有算分贡献。
  • filter：条件必须满足，但不算分，用于过滤，性能更高。
  • should：条件满足任意一个即可，有算分贡献。
  • must_not：条件必须不满足，不算分。

示例：查找标题或描述包含“Elasticsearch”，价格在 30 到 80 之间，且状态为“published”的书籍。

4. 聚合查询

聚合提供了对数据进行分组、统计和分析的能力，类似于 SQL 的 GROUP BY 和聚合函数。

kNN 与 BM25 Rescore

认识

1. kNN

在 kNN 向量检索出现之前，搜索主要依赖关键词匹配——你搜什么词，系统就找包含什么词的文档。这套机制在以下场景中显得力不从心：

  • 语义鸿沟：用户搜“性价比高的手机”，系统只认识“性价比”“高”“手机”这几个词，无法理解“划算”“实惠”“值”等语义相近的表达。
  • 非文本数据：图片、视频、音频等无法用关键词描述的内容，传统全文检索无能为力。
  • 推荐系统：需要根据用户行为找到“相似”的商品或内容，关键词匹配无法表达“相似”这个概念。

kNN 检索的核心解决方案是：将文本、图片、用户行为等一切数据转化为向量（一串数字），用向量之间的“距离”来衡量相似度。你搜“好吃的餐厅”，系统会把这句话转成向量，然后找到向量最接近的那些文档——哪怕文档里没有“好吃”这个词，只要语义相近（如“美味”“口碑不错”），也能被检索出来。

Elasticsearch 从 8.0 版本开始原生支持 kNN 向量检索。

2. BM25 Rescore

BM25 是 Elasticsearch 默认的相关性评分算法。它根据词频（TF） 、逆文档频率（IDF） 和字段长度来计算文档与查询的相关性。

但 BM25 有一个局限：它只能基于关键词匹配来算分。在复杂场景下，比如：

  • 用户希望“苹果手机”这个短语整体匹配，而不是“苹果”和“手机”分开匹配；
  • 用户希望用更复杂的模型（如机器学习排序模型）来重新排序；
  • 第一轮检索结果不够精准，需要第二轮精细化调整。

如果对所有文档都执行这些复杂计算，性能会急剧下降。

Rescore（二次打分）的核心解决思路是：先用廉价的 BM25 快速召回 Top N 个候选文档，然后只对这 N 个文档执行第二轮更精准（但更昂贵）的评分，重新排序。这就像海选先用简单标准筛一遍，决赛再用严格标准精评——既保证了质量，又控制了成本。

适用场景

技术 适用场景 不适用场景
kNN 语义搜索、图片/视频相似检索、推荐系统、异常检测、RAG 知识库问答 纯关键词精确匹配、数据量极小（< 几千条）、对解释性要求极高的场景
BM25 Rescore 需要二次精排的复杂搜索、短语优先匹配、结合业务字段（如热度）重新排序、多轮渐进式排序 数据量极小（不需要二次优化）、对实时性要求极高且无法接受额外延迟、排序逻辑在第一轮已完全满足

特别地：kNN 和 BM25 Rescore 经常组合使用——先用 BM25 做关键词召回 + kNN 做语义召回（混合搜索），再用 Rescore 对结果做二次精排，实现“召回层 + 精排层”的经典搜索架构。

Rescore（二次打分）

  • Rescore 是在第一轮搜索结果返回后，只对排名靠前的少量文档“再算一次分”，用更复杂的逻辑重新排序。
  • 使用：

window_size 控制参与重打分的文档数（默认 10），query_weight 和 rescore_query_weight 控制两轮分数的权重。

混合检索

完整的查询请求示例

注意：query_vector 里的 ... 是占位符，实际生产环境中是一长串几百位的浮点数（由 NLP 模型将“如何配置Redis集群”这句话转化而来）。

为什么需要“混合检索”？

假设你在公司内部知识库搜索“如何配置Redis集群”：

  1. 纯关键词检索（BM25）：它会老老实实找包含“配置”、“Redis”、“集群”这些词的文档。但如果有人写的是“Redis 集群搭建步骤”（没有“配置”二字），它可能就搜不到了。
  2. 纯向量检索（kNN）：它能读懂语义，知道“搭建”和“配置”是一回事。但它可能把权限搞混，把别人私密的“Redis故障演练”文档也推给你。

混合检索 = 左手抓关键词精确匹配，右手抓语义泛化理解，脚下还踩着“权限过滤器”防止越权，最后再用“精排算法”把最好的结果顶到最前面。

模块一："size": 10 —— 返回结果数

这是整个查询的“出口阀门”。无论中间过程捞出来 300 条还是 1000 条，最后返回给前端或用户的，只有 10 条。

模块二：knn —— 语义检索

  • field：你在建索引时，一定有个字段叫 vector，类型是 dense_vector，里面存着每篇文档的向量值。
  • query_vector：这是通过机器学习模型实时推理出来的向量。
  • k：向量检索这一路，先猛捞 300 个语义最像的文档。
  • num_candidates：为了性能，每个分片会先挑出 300 个“看起来像的”，再汇总挑出全局最优的 300 个。

模块三：query.bool —— 关键词硬匹配 + 权限安检（最重要的复合查询）

这是整个查询里最复杂的部分，由 must（必须匹配，算分）和 filter（必须匹配，不算分）组成。

① must 里的 match —— 全文检索（传统搜索引擎老本行）
  • 这个 match 会把“如何配置Redis集群”分词（比如分成：如何、配置、Redis、集群）。
  • 然后去 textContent 字段里找包含这些词的文档，并计算一个 相关性评分（_score），词频越高、越稀有的词，得分越高。
② filter 里的 bool.should —— 权限门禁（OR 逻辑，必须满足其一）

这里的逻辑翻译成人话就是：

只有满足以下条件之一的文档，才有资格进入候选池：

  • 作者 ID 是 42（你自己写的）；或者
  • 是公开文档；或者
  • 组织标签属于 “ENGINEERING / TECH_DEPT / COMPANY” 中的任意一个。

关键区别：filter 里的条件 不影响相关性评分，只做“硬过滤”。也就是说，哪怕这篇文档关键词匹配度 100 分，只要不通过这里的安全检查，就会直接舍弃。

模块四：rescore —— 二次精排

前面的 knn + query 已经产生了一个初步排名，但 Elasticsearch 觉得“不够精细”，于是启动重打分机制。

  • window_size: 300：大海捞针捞出来的几十万文档，我只关心当前得分最高的前 300 个，其他的不管了。
  • rescore_query：用 operator: "and" 重新匹配一次。这意味着，只有在 textContent 里 同时包含“如何”、“配置”、“Redis”、“集群”这四个词 的文档，才会在这个环节获得极高的加分。
  • 权重计算：最终得分 = 0.2 * 老分数 + 1.0 * 新分数。rescore_query_weight 设为 1.0（远大于 0.2），相当于用“必须全部包含关键词”这个硬标准，把最精准的文档强行提拔到最前面。

混合检索流程

  1. 并行双路召回：
    • 一路走 knn（向量），捞出 300 条语义相似的。
    • 一路走 query（关键词 + 过滤器），筛出所有符合关键词且通过权限验证的文档，并算出初步分数。
  2. 结果合并与粗排：
    • 系统将两路结果合并，去掉重复项，按初步分数（_score）排序，形成一个大的候选池。
  3. 截取前 300 名：
    • 从候选池中只取出当前排名最靠前的 300 个文档（由 window_size 决定）。
  4. 精排重算：
    • 对这 300 个文档执行 rescore_query（要求四个词全匹配），重新计算最终得分并排序。
  5. 输出最终结果：
    • 从精排后的前 300 名里，截取前 10 条（size: 10）返回给调用方。

调优建议

  1. k和 window_size 的关系：通常建议 window_size ≥ knn.k，确保向量捞回来的 300 条都能进入重打分环节。
  2. num_candidates 要大于 k：比如 k=300，num_candidates 可以设 500 或 1000，能提升召回率（但会增加性能开销）。
  3. query_weight 与 rescore_query_weight 的配比：如果你觉得关键词精确匹配更重要，可以把 rescore_query_weight 调得比 query_weight 大很多（就像本例中的 1.0 vs 0.2）。
  4. filter 里多用 term：对于精确匹配（如 ID、状态、标签），请务必用 term，千万别用 match，否则会被分词器拆散，导致权限越界！
