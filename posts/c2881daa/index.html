kafka实践教程

第一章 Kafka 核心概念

在切入业务代码前，需要先厘清 Kafka 的通信模型与基础组件。如果不理解这些设计动机，使用 KafkaTemplate、@KafkaListener 与 DefaultErrorHandler 时就容易陷入机械配置的误区。

1.1 同步调用的瓶颈

1.2 引入消息队列的收益

消息队列充当了调用方与处理方之间的缓冲媒介：

  1. 异步加速：将非强一致性的从属逻辑剥离出主响应链路，直接降低接口延迟。
  2. 系统解耦：上游只负责投递结构化事件，下游增减消费者（如新增风控系统）无需改动订单核心服务的代码。
  3. 流量削峰：当下游数据库最大承载能力为 1000 QPS，而瞬时请求激增到 10000 QPS 时，消息先在队列中持久化排队，消费者按自身处理能力匀速拉取，避免底层存储被瞬间压垮。

1.3 Kafka 消息模型与关键拓扑

Apache Kafka 是一套高吞吐、持久化、支持水平扩展的分布式事件流平台。在本项目中，各组件承载如下分工：

Broker 与集群

Broker 是 Kafka 的服务节点。生产集群通常由多个 Broker 协同工作以实现高可用；本 Demo 为简化部署，配置单节点服务监听于 localhost:9092。

Topic 与 Partition

Topic 是划分消息类型的逻辑主题，例如 order-events（正常事件）与 order-events-dlt（死信事件）。每个 Topic 可进一步切分为多个 Partition。

Partition 是 Kafka 保证并发能力与横向扩展的物理单元。单 Partition 同一时刻只能由同一 Consumer Group 内的一个消费者实例独占拉取。增加 Partition 数量，能够提升该消费组的消费并发上限。

单分区有序性

Partition 是仅支持顺序追加写（Append-only）的提交日志。消息按入队次序依次分配单调递增的偏移量：

Kafka 仅保证单个 Partition 内部的消息有序，不同 Partition 之间不存在全局顺序保证。

Offset

Offset 是消息在其所属 Partition 内的序列编号。它是相对概念，并非全局唯一 ID。定位一条物理记录的完整坐标为：Topic + Partition + Offset。消费者通过提交已消费的 Offset，向集群记录当前组在该分区的读取进度。

Consumer Group

同属一个 Consumer Group 的消费者协同消费一个 Topic。若 Topic 包含 3 个分区：

  • 组内有 1 个 Consumer 时，该实例同时处理 3 个分区；
  • 组内有 3 个 Consumer 时，每个实例分别独占消费 1 个分区；
  • 组内若启动 4 个以上的 Consumer，多出的实例将处于空闲待命状态。

若有两个不同的 Consumer Group（例如订单处理服务与数据分析服务）订阅同一 Topic，两组会完全独立地推进各自的 Offset，互不影响。

消息路由键：Key 的选择

Kafka 默认使用 Murmur2 算法对 Key 计算哈希，并对 Partition 总数取模，以此决定消息路由的目标分区。只要 Topic 的分区数量不发生变更，相同 Key 的消息将始终落入同一个 Partition。

如果使用每个事件唯一的 UUID 作为 Key，同一订单的“创建”、“支付”、“发货”可能会散落到不同分区，被不同线程并发处理，从而导致“支付先于创建被消费”的乱序问题。因此本项目强制将业务主键 orderId 设为 Kafka Key，以单分区有序性守住单订单的生命周期顺序；而将每次操作唯一的 eventId 留在消息体中，专门负责消费端的幂等排重。

ACK 与重复消费成因

ACK 是消费者向框架确认消息已处理完成的信号。在手动 ACK 模式下，代码必须在本地事务成功提交之后调用 acknowledge()。如果过早确认，后续业务执行抛出异常时，该消息在 Kafka 看来已被消费，将直接引发漏处理风险。

相反，如果业务处理已在 MySQL 中成功入库，但在执行 ACK 或框架提交 Offset 的瞬间进程宕机，Kafka 由于未收到确认，在消费者重启后仍会自上次已提交的 Offset 处重新投递该消息。这种“处理成功但确认丢失”的边缘场景，决定了消费端必须设计业务幂等防线。

临时重试与死信队列（DLT）

网络抖动或短时死锁属于瞬时异常，通常在重试一到两次后即可自愈；而 JSON 结构损坏属于永久性异常，原地无限重试只会白白占用线程与数据库连接，甚至造成单分区阻塞（即毒消息，Poison Message）。因此系统需要实施有限退避重试，耗尽重试次数后将数据投递至死信队列（order-events-dlt），隔离异常并交由告警系统介入。

开启生产端原生幂等后，Kafka 客户端会为每个 Producer 实例分配唯一的 PID，并为发送到每个分区的消息维护单调自增的 Sequence Number。一旦因网络丢包导致客户端未收到 Broker 确认并自动重试，Broker 端可根据 PID 与序列号过滤掉重复追加的记录。需要注意，这只防范了 Producer 到 Broker 链路的写入重复，不能解决消费端的业务重复问题。

为什么选择手写 JSON 序列化？

Spring Kafka 提供了开箱即用的 JsonSerializer，但其默认会在 Record Header 中塞入全限定 Java 类名，导致不同微服务间存在强类路径耦合。直接将领域对象通过 Jackson 序列化为规范 JSON 字符串，再交给 StringSerializer 转化为字节流，能够让报文保持通用与透明，降低跨系统通信时的解析摩擦。

4.3 消费端与进度控制

默认的自动提交是基于固定时间窗口（如每 5 秒一次）提交已拉取到的最大 Offset。如果在处理一批消息的中途系统突然重启，后半部分未处理完成的消息由于进度已被提前提交，将彻底丢失。将其关闭并设置为 manual_immediate，意味着消费端由业务代码明确驱动 Offset 提交，只有当一段消息的处理逻辑真正跑通，位点才被推向 Broker。

当一个全新的 Consumer Group 首次接入，或者其原有的位点已在集群中过期淘汰时，该参数决定读取策略。earliest 表示从该分区当前尚存的最早位点开始回放；latest 则只接收启动之后新追加的消息。若该消费组在集群中已存在有效的提交记录，Kafka 将始终沿用现有进度，不会盲目从头全量读取。

4.4 Topic 编排

通过 Spring 容器管理 NewTopic，应用在启动时会自动补全缺失的主题定义。分区数设为 3，意味着当前消费组最多可由 3 个工作线程并发分工消费。副本因子受限于单节点 Broker 环境，在此设置为 1。

5.2 发送行为与模式对比

发送消息通常有三种交互方式：

  1. 发后即忘（Fire-and-forget）：调用 send() 后不处理返回值。响应极快，但在网络故障时无法感知投递丢失，可靠性最弱。
  2. 同步阻塞（Synchronous）：调用 send().get() 显式等待服务端应答。吞吐量极低，线程常年阻塞于网络 I/O，违背了事件驱动的初衷。
  3. 异步回调（Asynchronous Callback）：使用 whenComplete() 注册监听逻辑。业务主线程向底层发送缓冲区追加消息后即可继续向下执行，底层的 I/O 线程会在收到 ACK 时异步触发相应回调，兼顾吞吐与可观测性。

6.2 异常传递与位点提交控制

编写 Consumer 时最常见的误区是随意包裹大粒度的 try-catch (Exception e) 并在 catch 块中仅打印一条日志后继续向下执行。这会导致异常被内部消化，Spring Kafka 容器认为本轮消费正常结束，进而触发 ACK 并推进 Offset，最终使得失败的消息在不知不觉中被跳过。

正确的做法是让业务异常向外抛出至容器层。Spring Kafka 拦截到未处理异常后，会中止本次位点确认，并将其转交给配置好的 DefaultErrorHandler 执行后续重试或降级分流。

第七章 重试与死信队列

7.1 异常的区分与分流策略

生产环境中的消费异常大致可归为两类：

  • 瞬态故障（Transient Failure）：如数据库连接池打满、慢查超时、微服务网络毛刺。这些错误通常在数秒内具备自愈可能，应当使用退避策略原地重试。
  • 确定性故障（Deterministic Failure）：如业务载荷字段缺失、JSON 字符串破损、数字反序列化溢出。这类输入无论尝试多少次结果均不会发生改变，盲目重试只会消耗系统资源，必须直接拦截并路由至死信队列。

7.2 错误处理器配置

setCommitRecovered 的必要性

当一条消息耗尽所有重试机会并成功转储至 DLT 后，setCommitRecovered(true) 会通知容器自动提交该原消息在业务 Partition 的 Offset。若未开启此项，消费者实例一旦在后续某个时刻发生重平衡或重启，仍会从这条未提交的“毒消息”处重新拉取，从而再次陷入无效的死循环。

第八章 幂等消费与事件去重

8.1 为什么必须在业务层做幂等

在分布式环境下，Kafka 遵循 At-Least-Once（至少投递一次）语义保证。只要网络层面存在抖动可能，消息的重复消费就是不可避免的客观规律。

配置了 enable.idempotence = true 的 Producer 只能确保同一个消息批次写入 Kafka 日志时不重复；一旦 Consumer 处理完毕但位点在返回提交时由于断网未能打到 Kafka，这条记录在重新平衡或重启后必会被二次投递。

8.2 基于本地事务的去重实现

为什么去重记录与业务操作必须绑定在同一个 @Transactional 中？

假设将去重标志写入内存 Set，或在非事务环境下提前独立写入去重表：

  1. 消费端拉取消息，在去重表中插入了记录；
  2. 随后在执行业务落库或外部逻辑时抛出异常崩溃；
  3. 本次消费流程失败中断，Kafka 触发稍后重试；
  4. 重试拉取同一条消息再次执行，此时由于去重表中已存在记录，系统直接返回 DUPLICATE 并确认位点。

这会导致订单实际根本没有创建，业务数据彻底丢失。只有将 processed_event 和 orders 划入同一个本地事务，当业务出现异常回滚时，去重占位记录才会一同被撤销；只有当下一次重试真正通盘走完，两者才同步固化进磁盘。

第十章 生产环境最佳实践

10.1 轮询生命周期参数管理

max.poll.records

定义了消费者底层单次调用 KafkaConsumer.poll() 允许返回的最大数据条数（默认 500）。如果单次拉取数据过多，而每条业务处理耗时较长，整批任务的总耗时就可能超出心跳保护期。因此耗时较重的任务应当主动调低该阈值。

max.poll.interval.ms

两次 poll 之间允许的最大时间跨度（默认 5 分钟）。如果某批记录处理过慢导致超过该阈值，Kafka 集群会判定该消费者工作线程已挂死，直接将其踢出 Consumer Group 并触发 Rebalance，导致该分区的任务被频繁重新指派并二次执行。

10.2 重平衡（Rebalance）与规避

Rebalance 是 Consumer Group 重新分配分区的过程。触发条件包括：

  • 组内实例扩容、缩容或滚动发布重启；
  • 某个实例因 Full GC 暂停或业务长时阻塞，导致心跳超时（session.timeout.ms）或轮询超时（max.poll.interval.ms）；
  • 订阅的主题发生了分区扩容。

发生频繁重平衡期间，消费者需要挂起当前工作重新认领分区，易造成消费抖动与 Lag 攀升。规避手段包括设置合理的 GC 策略避免长暂停、调大心跳超时窗口、并将耗时过长的非核心业务（如第三方支付验证）异步化。

10.3 消费积压（Consumer Lag）的排查路径

当监控平台发出 Lag 持续增长告警时，排查次序通常如下：

  1. 检查消费状态：确认工作节点是否存在大量错误重试日志，或者发生频繁 Rebalance；
  2. 分析耗时瓶颈：排查数据库是否有慢查引发了线程池等待，或者外部 RPC 调用出现高延迟；
  3. 核算并行度上限：如果所有消费者节点 CPU 与 I/O 正常，仅为纯粹的业务流量突增，应评估当前的分区数。若 Topic 仅有 3 个 Partition，盲目将消费者实例堆到 10 个没有任何效果，必须同步扩充 Partition 数量后再做横向水平扩容。

10.4 消息契约演进原则

生产系统不可避免需要变更报文格式，制定演进规范尤为重要：

  • 只增不减：只允许向报文中新增可为空的字段，严禁删除已有字段或变更现有字段的物理类型；
  • 宽容解析：消费端 ObjectMapper 应当启用反序列化忽略未知属性配置，避免生产端发出新属性时下游全线崩溃；
  • 复杂体系契约治理：对于跨部门的大规模微服务架构，可逐步引入 Apache Avro 或 Protobuf，依托 Schema Registry 服务在集群服务端进行 Schema 兼容性强校验。

附录 A 常见问题排查

A.1 为什么消费端始终无法拉取到消息？

依次排查以下节点：

  1. 执行 kafka-topics --list，确认投递的主题名称拼写是否一致；
  2. 执行 GetOffsetShell 检查该主题分区的 LOG-END-OFFSET 是否在持续递增，确认消息是否真正写进了集群；
  3. 执行 kafka-consumer-groups --describe --group <group-id>，核对当前消费组的分配拓扑，排查是否由于组内节点数量多于分区数导致当前节点处于空闲状态。

A.2 为什么修改了 group-id 后旧消息全部重新被消费了一遍？

当更换了全新的 group-id 时，Kafka 会认为这是一个完全未曾见过的消费群体。由于该群体在服务端不存在任何已提交的 Offset 记录，客户端将退回并应用 auto-offset-reset: earliest 的策略，从当前依然保存在日志中的最老位点从头回放全量数据。

A.3 为什么增加消费者节点后消费速率毫无变化？

Kafka 的核心分配约束是：同一个 Consumer Group 内，单个 Partition 在同一时刻只能指派给唯一的 Consumer 线程。如果主题只有 3 个分区，那么组内最多只有 3 个消费者在并行工作。继续追加节点只会使其陷入无分区可分配的闲置状态，必须对 Topic 执行分区扩容才能解锁更高的并行度。

附录 B 关键配置速查表

B.1 核心概念边界判定

概念 核心定位 核心防线
orderId 业务主键 / Kafka Key 决定消息散列的分区，守住单订单维度的有序处理
eventId 操作唯一标识 (UUID) 存入去重表 processed_event，防止重复消费产生业务副作用
Partition 物理并发与存储单元 决定 Consumer Group 消费吞吐量的并发上限
Offset 单分区日志递增位点 供消费者标记当前分区的进度，作为故障恢复的基点

B.2 三种幂等与事务的边界区分

  • Producer 幂等 (enable.idempotence = true)：利用内部 PID 与 Sequence Number，消除生产客户端向 Broker 投递时因网络重试引发的日志重复写入。
  • Consumer 幂等 (processed_event 约束)：解决消费端在接收到多次重复投递时，防止业务执行（如扣款、插表）产生重复副作用。
  • 本地事务 (@Transactional)：确保“去重标记插入”与“订单业务插入”在本地数据库中同生共死。业务异常回滚时，去重记录同步消失，从而保证后续的重试得以正常重入。
