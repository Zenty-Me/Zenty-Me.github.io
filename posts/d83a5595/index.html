GitHub Pull Request 完全指南：从创建分支到代码合并

适合读者：刚接触 Git/GitHub 协作、需要向团队项目提交代码或参与开源贡献的开发者。本文以 Go 项目为例，但 Git 工作流适用于绝大多数语言和项目。

你已经修改了一个项目，接下来如何把代码提交给维护者审核？答案通常是创建 Pull Request（简称 PR）。本文从最基础的概念讲起，完整演示两种常见场景：你有项目的写入权限，以及你需要通过 Fork 给别人的开源项目贡献代码。

配图说明：GitHub 操作界面采用 GitHub 官方文档的公开 HTTPS 截图；流程图采用内嵌 Mermaid 代码块，不依赖 Mermaid Ink 图片服务，也不需要本地图片文件夹。Typora 中如未显示流程图，请在偏好设置中开启图表（Mermaid）功能；不同博客平台对 Mermaid 的支持不同，正式发布时请先预览。

一、PR 究竟是什么？

PR 是向代码仓库发起的合并请求：告诉维护者“我在某个分支完成了这些修改，希望你们审核后将其合并到目标分支”。创建 PR 本身不会自动合并代码，它提供的是代码比较、讨论、自动化检查和审查的平台。

理解两个角色就够了：

  • base（目标）：你希望代码最终进入的仓库和分支，如原项目的 main。
  • compare（来源）：保存你修改的仓库和分支，如你的 fix/api-timeout。

二、场景 A：你对项目有写入权限

如果你是团队成员，可以直接在项目仓库中创建分支并推送。下面假设目标分支为 main，修改内容是修复 API 超时问题。

第 1 步：确认仓库与工作区状态

通过 git status 确认没有意外的未提交修改。如果有尚未完成的工作，可以先提交到当前分支，或者在确认内容后使用 git stash 暂存；不要直接运行可能覆盖改动的命令。

第 2 步：同步目标分支

--ff-only 只接受快进更新，避免在同步时意外生成额外的合并提交。如果项目的目标分支不是 main，请替换为实际分支。

第 3 步：创建开发分支

每个独立功能或问题使用单独分支，便于审查和回滚。常见命名习惯如下：

前缀 适用场景 示例
feat/ 新功能 feat/user-login
fix/ Bug 修复 fix/api-timeout
refactor/ 不改变外部行为的重构 refactor/database-layer
docs/ 文档变更 docs/update-readme
test/ 测试补充 test/api-errors

三、场景 B：向别人的开源项目提交 PR（Fork 工作流）

如果你没有原项目的写入权限，一般先在 GitHub 网页点击 Fork，将原项目复制到自己的 GitHub 账号下，然后把分支推送到自己的 Fork，再向原项目发起跨仓库 PR。

五、PR 提交后，如何处理审核意见？

创建 PR 并不代表工作结束。维护者可能要求你调整代码或补充测试，这时通常不需要重新开一个 PR。

流程示意：在原开发分支提交新 Commit 并 Push，即可更新同一个 PR。

保持在提交 PR 的原分支，继续修改、检查，然后提交并推送：

新的 Commit 会自动出现在现有 PR 中。检查 CI 结果、回复审核评论，确认所有必要检查和审查通过后，再依照项目权限和规范合并。

如果开发期间目标分支有新提交，先与团队确认使用 Merge 还是 Rebase。对已经共享的分支执行 Rebase 后，可能需要强制推送；不要不加判断地对团队共用分支使用 git push --force。

六、常见问题与排查

1. git push 提示 Permission denied

常见原因包括：没有目标仓库的写入权限、SSH 密钥或 HTTPS 凭据未配置、远程地址指错仓库。先检查：

如果是开源项目且没有写入权限，应使用 Fork 流程，而不是尝试直接推送到原项目。

2. GitHub 页面上没有 Compare & pull request

可以手动进入 Pull requests → New pull request。检查分支是否成功推送、是否正确选择 base/head，以及两个分支之间是否确实存在可比较的提交。

3. PR 显示合并冲突

说明你的分支与目标分支的部分改动无法直接自动合并。先读取项目贡献指南，确认允许的同步方式；然后从目标仓库获取更新，选择合适的 Merge 或 Rebase 策略解决冲突。处理冲突后运行相关测试，再提交/推送。

4. PR 的 CI 检查失败

打开 PR 的 Checks 页面查看失败任务与日志。不要只看“红灯”，要定位是代码错误、依赖问题、测试环境故障还是仓库已有问题。修复后推送到同一分支，新的检查通常会自动触发。

5. PR 里出现大量无关文件

提交前检查 git diff、git diff --cached 和 git status。如果误把无关文件暂存了，可以使用 git restore --staged <文件路径> 将其移出暂存区；这不会删除工作区中的修改。若已经提交并推送，应谨慎处理历史，尤其是与他人共享的分支。

七、提交 PR 前的检查清单

  • [ ] 已阅读项目的 README.md / CONTRIBUTING.md / PR 模板。
  • [ ] 已确认目标仓库和目标分支，基于正确分支创建开发分支。
  • [ ] 修改范围聚焦，不包含无关文件或敏感信息。
  • [ ] 已按项目要求完成格式化、构建、测试和静态检查。
  • [ ] 已逐项检查 git diff 与暂存区变更。
  • [ ] Commit 信息清晰，开发分支已成功推送。
  • [ ] PR 的 base/head 方向正确，标题、修改说明、验证过程完整。
  • [ ] 已检查 CI 结果，并准备根据 Review 反馈继续更新。
